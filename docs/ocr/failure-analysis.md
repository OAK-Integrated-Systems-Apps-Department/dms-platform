# OCR Failure Analysis

Section 1 deliverable of `docs/ocr/ocr-production-prompt.md`. Reproduces the upload failures against the running local stack and confirms/refutes the 10 hypotheses in that document's section 1, plus the required file-type batch. No code was changed to produce this document.

## 1. Method

**Stack:** local `docker compose` stack (`infra/local`), commit state as of 2026-09-23, ocr-worker image as last rebuilt this session (includes this session's own earlier fixes: render-cap 1600px, docx support, extraction accuracy fixes). All services healthy for the full test window; `oakdms-ocr-worker` baseline before testing: `OOMKilled=false`, `RestartCount=0`.

**Trigger paths used:**
- **Direct-to-ocr-worker** (`POST /ocr/process/{version_id}`, `X-Internal-Token` auth), via a new script `scripts/dev/repro_batch.py` (sibling to the existing `smoke_test_ocr.py`, same bootstrap-fixture-as-document-version pattern). This is the path actually exercised for every fixture in section 3 below — it bypasses dms-core/Keycloak auth entirely (same reason `smoke_test_ocr.py` does), isolating worker-internal behavior from the Java trigger layer.
- **Real HTTP upload path** (`POST /api/v1/documents` → `triggerOcrAsync`): not re-driven fresh in this batch (would need a throwaway Keycloak-authenticated test user, out of scope for this pass). Instead, hypothesis 1 and the MIME-trust half of hypothesis 4 are evidenced by **real production incidents already captured earlier in this same session** against this same environment — a real JPEG upload (`Ayushi_channelling.jpeg`) and a real invoice upload (`Thusitha invoice.pdf`) both hit dms-core's 60s `OcrWorkerClient` timeout while ocr-worker kept running and later completed successfully, with exact log lines captured at the time (`OcrWorkerClient : Could not reach ocr-worker ... Read timed out`, followed minutes later by real extracted field values in the DB). That evidence is cited directly below rather than re-created synthetically.

**Fixtures:** the 3 existing real fixtures in `backend/workers/ocr-worker/tests/fixtures/` (`native_text.pdf`, `scanned_image_only.pdf` ~11.2MB, `scanned_image.png`) plus 15 newly constructed ones (`scripts/dev/build_fixtures.py`, run once inside the ocr-worker container — Pillow/pypdf/pillow-heif/python-docx). Full construction method per file type in §3.

**Evidence captured per case:** `docker logs`, `docker inspect` (OOMKilled/RestartCount), `docker stats` (1s polling during concurrent runs), and direct `psql` queries against `document_versions`, `processing_jobs`, `outbox_events` — both immediately after any client-side timeout and again once the worker genuinely finished.

**Peak-memory measurement (feeds Phase 1's `mem_limit` sizing):** a 4-concurrent run (`scanned_image_only.pdf`, `phone_photo_large.jpg`, `multipage.tiff`, `rotated_90.png`) polled every 1s throughout. **Peak observed: 3.763 GiB** (baseline ~2.36GiB carried over from the prior sequential run, not yet GC'd — true from-idle peak is likely somewhat lower). **Important caveat for Phase 1**: this number reflects *today's* architecture, one shared PaddleOCR/Docling instance across all concurrent requests. Phase 1's process-pool design gives each of `OCR_WORKER_PROCESSES` processes its **own** full model set — that will very likely raise peak memory, not lower it (N processes × per-process model footprint, rather than one shared footprint serving N requests). Treat 3.763GiB as a floor / sanity check, not a direct `mem_limit` value — re-measure once the process pool exists.

## 2. Hypothesis findings

### 2.1 Synchronous HTTP bypasses RabbitMQ, races, no reaper — **CONFIRMED**
Static evidence (unchanged from code review): `OcrWorkerProperties.readTimeoutMs=60000`; zero RabbitMQ publish anywhere on the upload path; zero `@Scheduled` reaper anywhere in dms-core.
**Live evidence (this session, real documents, same environment):** two real uploads (`Ayushi_channelling.jpeg`, `Thusitha invoice.pdf`) both produced the exact race: dms-core logged `Could not reach ocr-worker ... Read timed out` and marked the version `failed`, while ocr-worker kept running and completed successfully minutes later with real extracted data sitting unread until a later poll reconciled it.
**New live evidence (this batch, direct-to-worker path, precise timing):** `large_35page_scanned.pdf` — client gave up at **189.6s** (180s configured timeout + teardown), but the worker's own `processing_jobs` row shows `started_at=06:20:34.558`, `finished_at=06:29:39.550` — **544.99s real processing time**, i.e. the worker kept running for **~355 more seconds after the caller had already abandoned the request**, and still succeeded (`status='completed'`). `corrupt_truncated.pdf` shows the identical pattern: client timeout at 189.7s, real completion at 268.7s.
**Related new finding, not one of the original 10:** because the whole `process_version` call runs inside one DB transaction (§2.3), the **outbox event's own `created_at` timestamp is frozen at the transaction's start**, not when the row was actually inserted — Postgres's `now()`/`CURRENT_TIMESTAMP` returns one fixed value for the life of a transaction. Verified: `large_35page_scanned.pdf`'s `.completed` outbox row has `created_at=06:20:34.557` (matching job `started_at`, not the real `finished_at` 06:29:39) while `published_at=06:33:35` (set later, by the separate `OutboxRelay` poller using real wall-clock time) is accurate. **This means the outbox audit trail's own `created_at` is misleading for any job whose transaction spans a long inference** — a second, compounding symptom of the same long-held-transaction design, worth fixing alongside hypothesis 3.

### 2.2 Shared, non-thread-safe models, racy lazy init — **CONFIRMED**
Static evidence unchanged (one `LayoutEngine`/`PaddleOcrEngine` shared across FastAPI's threadpool and the consumer's `ThreadPoolExecutor`; unlocked check-then-set lazy init).
**Live evidence:** the 4-concurrent run completed all 4 requests successfully (no crash, no corruption observed) but with clear, real contention slowdown: `scanned_image_only.pdf` took 29.5s solo (sequential run) vs **80.3s** under 4-concurrent load — 2.7x slower. The accidental overlap between `large_35page_scanned.pdf` (running 06:20:34–06:29:39) and `corrupt_truncated.pdf` (running 06:24:14–06:28:42, entirely inside that window) shows the same effect even more starkly: a 1-page truncated PDF that should complete in a few seconds to tens of seconds took **268.7s** while sharing the worker with the 35-page job. No crash or wrong-output was observed in this batch, but the magnitude of slowdown under only mild concurrency (2-4 simultaneous requests) confirms real contention on the shared model objects, consistent with the hypothesis even though outright corruption wasn't triggered this round.

### 2.3 DB transaction held open during inference — **CONFIRMED**
Static evidence unchanged (Docling conversion + PaddleOCR inference run entirely inside `with session_scope(...)`).
**Live evidence:** directly demonstrated by §2.1's outbox-timestamp finding above — a transaction that's still open 9 minutes after it started is about as concrete as this gets.

### 2.4 Client-supplied MIME type trusted, tiny supported set — **CONFIRMED**
Static evidence unchanged (`file.getContentType()` trusted verbatim in dms-core; `SUPPORTED_MIME_TYPES` has 5 entries).

**Live evidence, direct-to-worker (synthetic mime_type):** `phone_photo.heic` (a real HEIC bitstream, built via `pillow-heif`) sent to `/ocr/process/{id}` with an explicit `image/heic` mime_type was rejected in **0.08s** with `last_error='image/heic'` (the raw `UnsupportedMimeType` string) — confirms fast/clean rejection, no hang, no crash.

**Live evidence, real upload through the actual My Documents page (dms-core's own MIME handling, not synthetic):** the same HEIC file was uploaded through the real frontend (`http://localhost:3000/documents`), logged in as the real seeded user, going through the genuine `DocumentServiceImpl.uploadDocument` → `triggerOcrAsync` path. **The browser itself reported `application/octet-stream` as the file's Content-Type — not `image/heic`** (confirmed via `document_versions.mime_type` in the DB: `87b307c8-b8c2-46a3-8986-3b0c81266534 | application/octet-stream | failed | phone_photo.heic`). This is because Chrome has no registered MIME type for `.heic` and falls back to the generic default — meaning **the real-world failure mode for HEIC uploads is the `application/octet-stream` case, not a `image/heic`-specific rejection at all**, confirming the hypothesis's `application/octet-stream` example directly via a real device-realistic upload path, not just a synthetic one.

The frontend UI result is also now confirmed live: the document shows status **Failed** with the message *"OCR could not process this document. You can still fill in fields manually, or retry below."* — the same generic, non-specific message regardless of cause, with a "Retry" option that (per this failure's nature — a permanently unsupported format) can never succeed. This is a real, live-confirmed UX gap: the user has no way to know their file type just isn't supported at all, and is invited to retry something that will never work. Directly informs Phase 1's error-code taxonomy (§B.6) and the `UNSUPPORTED_FORMAT` code should suppress the "Retry" affordance in the frontend once threaded through.

**`image/jpg` (non-standard alias) not independently re-tested live:** real browsers normalize `.jpg`/`.jpeg` file uploads to the standard `image/jpeg` via the File API — Chrome will not itself produce the `image/jpg` variant from a local file picker. That alias realistically arrives only from non-browser clients (mobile apps, direct API callers, older camera firmware), which is exactly why dms-core-side normalization (not just browser-side) remains necessary per Phase 1 §B.5 — confirmed as a server-side concern, not something further browser-based testing would add evidence for.

### 2.5 Render cap too aggressive for small print — **CONFIRMED** (unchanged from this session's own earlier fix)
`_MAX_RENDER_DIMENSION_PX=1600` ≈137-145 DPI for Letter/A4, not the ~180 DPI the code's own comment claims (independently recomputed, comment is wrong). No new live evidence needed — this was directly observed and fixed earlier this session with real documents.

### 2.6 Bbox coordinate spaces disagree — **REFUTED** (mechanism), real adjacent gap noted
Confirmed refuted: native_text vs. paddleocr dispatch is mutually exclusive per page, so no single page mixes capped/uncapped coordinate scales.
**Noted gap (not the hypothesized mechanism, but real):** pixel bboxes carry **no recorded page-scale/DPI reference** anywhere in the output JSON. A page's own blocks are internally consistent, but nothing downstream (e.g. a future review-UI highlight renderer) can reconstruct "what physical size did this pixel bbox assume" without independently reproducing ocr-worker's exact cap/DPI math for that specific page. This is a real, separate limitation from what was hypothesized — Phase 2's normalized (0–1 fraction) coordinates are the actual fix, not anything Phase 1 should attempt.

### 2.7 Orientation disabled — **CONFIRMED** (whole-page) / **PARTIAL**
Static evidence unchanged: `use_doc_orientation_classify=False`, `use_doc_unwarping=False`; `use_textline_orientation=True` IS on (per-line only, not per-page).
**Live evidence:** `rotated_90.png` (a scanned raster image rotated 90° before OCR, no orientation correction applied) came back with **zero extracted fields** (`"fields": {}`) and `flags.low_confidence=true, requires_review=true` — a concrete, practical demonstration that a sideways scan meaningfully degrades extraction, not just a theoretical config concern.
**Contrast worth noting:** `rotated_native_text.pdf` (same 90° rotation, but applied as PDF page-rotation *metadata* on a **native-text** page) extracted its fields perfectly (`invoice_number: INV-77001`, `total_amount: 225.00`, etc.) — because native-text extraction reads the PDF's content stream directly and is indifferent to the `/Rotate` flag's visual effect. **Orientation only matters for the PaddleOCR/raster path**, exactly as the hypothesis implies, and this batch shows both the failure case (raster) and the unaffected case (native text) side by side.

### 2.8 Binary native-vs-scanned decision, no garbage filter — **CONFIRMED**
Unchanged from static review: any non-empty Docling text (even one garbage `TextItem`) takes the native_text path unconditionally; confidence hardcoded to 1.0 regardless of content quality. No live repro attempted this round (would need a deliberately hybrid/garbage-text-layer PDF, not yet constructed) — flagged as a good candidate fixture for a follow-up pass.

### 2.9 Whole-PDF Docling conversion, no chunking, raw exceptions — **PARTIALLY TRUE** (confirmed live, with real examples of the "raw exception" gap)
No chunking confirmed (unchanged). **Live evidence for the "raw, unclassified error" half:**
- `password_protected.pdf` → real Docling-internal exception, caught and recorded verbatim: `"Conversion failed for: tmpbsk1lba2.pdf with status: failure. Errors: docling-parse could not load document 8046c8d1...: Failed to load document with key key=8046c8d1..."` — technically accurate but not a message any end user or support engineer should ever see, and gives no actionable `ENCRYPTED_PDF`-style code.
- `corrupt_tiny_fragment.pdf` (a 200-byte truncated fragment — the only corruption class in this batch severe enough to actually fail; see next paragraph) → PyMuPDF's own raw message, again recorded verbatim: `"Failed to open file '/tmp/tmpfjrndh0f.pdf' as type pdf."`

Both confirm the hypothesis's core claim precisely: **the failure IS caught (not a crash — `process_version`'s broad `except Exception` works exactly as designed) but surfaces as an opaque internal string, not a classified error code.**

**Notable, unplanned finding on corruption severity:** three separate corruption techniques were tried against a real PDF (50% truncation, trailer-region byte-flipping, header-magic-bytes replacement) and **all three were silently repaired/tolerated by PyMuPDF's own lenient parser** — the file opened, and in the 50%-truncation case (`corrupt_truncated.pdf`) Docling even fully converted it and extracted real text, with only `MuPDF error: format error: object is not a stream` warnings logged (not raised). Only a much more severe truncation (200 bytes, no valid xref/trailer structure at all) actually raised an exception. **This means real-world "corrupt" PDFs may fail far less often than assumed** — worth tempering how much engineering effort the `CORRUPT_FILE` code deserves relative to the other 7 codes; `ENCRYPTED_PDF` (which failed reliably and immediately) is the higher-value case of the two.

### 2.10 Hardcoded field confidences, 0.95 threshold — **CONFIRMED (literals, static evidence)** / **not re-verified live this round — scoping gap, noted**
Static evidence unchanged and still stands: `extraction.py`'s `_extract_field_value` (the **selectable-fields** path) returns fixed literals (0.85/0.9/0.65/0.75/0.8/0.6/0.55) independent of real OCR token confidence; separately, `min_confidence_threshold=0.95` is a mean of *per-page* confidence (native pages fixed at 1.0), distinct from the field-level `field_low_confidence_threshold=0.6`.
**Scoping gap in this batch:** every request in this repro round was a bare `POST /ocr/process/{id}` with **no `requested_fields` body**, which routes through the **legacy** `extract_structured_fields` path — this path already derives its confidence from real OCR `base_confidence` (e.g. this batch's live results show real, non-round numbers like `0.7254185563988156`, `0.9977838024497032` — clearly not the selectable-path's hardcoded literals). **The hardcoded-literal claim was not exercised live this round** since doing so requires passing `requested_fields` in the request body. Recommend a fast follow-up rerun of a subset of these fixtures with `requested_fields` populated, to see the hardcoded literals live rather than relying on static code reading alone.

## 4. Prioritized fix list (feeds Phase 1 scope)

1. **Sync HTTP trigger + no reaper (H1)** — highest priority. Directly causes incorrect `failed` status on documents that actually succeed, and a genuinely stuck `processing` state is possible if the worker crashes mid-job with nothing to notice. Live-proven twice this session with real documents, and precisely timed in this batch (355s of unsupervised worker time after client abandonment).
2. **Shared model contention under concurrency (H2)** — no crash yet, but 2.7x–9x slowdowns under only 2-4 concurrent requests will make the sync-HTTP timeout problem (H1) dramatically worse as load increases; compounds directly with item 1.
3. **DB transaction held open for the full inference (H3)** — the mechanism behind both H1's race and the newly-found outbox-timestamp corruption; fixing this is largely a prerequisite for a correct reaper/lease design.
4. **MIME trust + tiny format allow-list (H4)** — real, common formats (HEIC in particular, now that phones default to it) are rejected outright; live-confirmed fast/clean failure, so this is a pure capability gap, not a stability risk.
5. **No error-code taxonomy (H9's practical impact)** — two real, distinct failure causes (encrypted PDF, corrupt file) both surfaced as raw, unclassified internal exception text; live-captured examples of both should seed the error-code design directly.
6. **Orientation handling for the OCR/raster path (H7)** — live-confirmed to zero out field extraction entirely on a rotated scan; real accuracy impact, though scoped to Phase 2 per the spec (preprocessing), Phase 1 should at minimum ensure this fails toward `low_confidence`/review rather than silently returning empty fields with no signal as to why.
7. **Hardcoded confidences (H10)** — confirmed via static evidence; live re-verification (with `requested_fields`) is a cheap, worthwhile follow-up before Phase 3 designs the calibrated-confidence replacement.

## 5. Explicitly out of scope for Phase 1

Per `docs/ocr/ocr-production-prompt.md` §6 and this session's own Phase 1 design (`cosmic-discovering-cray.md` plan): render DPI/resolution changes, PaddleOCR tiling, quality assessment (blur/contrast/skew), preprocessing (deskew/perspective/denoise — the real fix for H7's live-confirmed impact), per-page hybrid routing (H8's real fix), coordinate normalization (H6's noted gap's real fix), anchor-relative zones, invoice line-item extraction, LLM extraction tier, confidence calibration formula (H10's real fix), searchable PDF rendition, review-queue UI, LibreOffice conversion. These are all real, evidenced gaps — this document establishes that they're real, not that Phase 1 should attempt them.
